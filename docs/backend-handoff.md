# Backend: начало работы Артура

## Структура

| Путь | Назначение |
| --- | --- |
| `app/main.py` | Фабрика приложения, lifespan engine, обработчики ошибок |
| `app/core/config.py` | Типизированные настройки из env |
| `app/db/base.py` | Общая ORM Base, имена ограничений |
| `app/db/session.py` | Engine и жизненный цикл Session |
| `app/api/dependencies.py` | `get_session` для `Depends` |
| `app/api/v1/router.py` | Подключение бизнес-роутеров |
| `app/models/` | ORM-модели; импортировать каждую в `__init__.py` |
| `app/schemas/` | Pydantic-запросы и ответы |
| `migrations/versions/` | Версионируемые изменения БД |
| `tests/` | Unit- и интеграционные тесты |

Session выделяется на запрос. Успешную запись завершать явным `session.commit()`;
незавершённая транзакция откатывается при закрытии. Не использовать
`Base.metadata.create_all()` вместо миграций. URL и engine создаются при запуске,
соединение проверяется через `/health`. Закрытие приложения освобождает pool.

## Задачи Артура в первом спринте

1. Добавить модели `User` и `Pet`, JSON-схемы ответа без секретных полей.
2. Сгенерировать миграцию, прочитать полученный SQL и проверить откат.
3. Добавить `GET /api/v1/demo/pets` на вымышленных данных и тест контракта.
4. Передать изменения Вове на review. До появления кода review не выполнен.

Предложение по модели: UUID `id`, UTC `created_at`, имя пользователя и уникальный
email; у питомца имя, вид, nullable дата рождения и создатель. Не выдавать питомцев
по клиентскому `user_id`. Для будущего совместного доступа не считать создателя
единственным возможным участником: отдельно предусмотреть связь семьи/участников
и питомцев. Членство и права не добавлять в первом спринте как фиктивную защиту;
перед пользовательским CRUD во втором спринте Вова реализует проверку доступа.

## Миграции

Запускать из `backend/` с доступной БД и установленными зависимостями:

```sh
alembic upgrade head
alembic revision --autogenerate -m "add users and pets"
alembic upgrade head
alembic check
alembic current
```

`0001_baseline` намеренно не создаёт доменных таблиц: это старт цепочки, чтобы
Артур добавил свои модели следующей миграцией. Alembic создаёт `alembic_version`.
На одноразовой тестовой БД проверить `alembic downgrade base` и повторный upgrade.
Не менять уже применённые миграции и не запускать downgrade на данных команды.

Review: соответствие моделей контракту, nullable и ограничения, индексы/FK,
импорт моделей в metadata, upgrade/downgrade, отсутствие секретов в ответах,
тесты успешного ответа и ошибок. Изменение схемы согласовать с Вовой до merge.
