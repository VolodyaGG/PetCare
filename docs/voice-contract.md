# Голосовой контракт v2

Согласованная форма первого прототипа: запись → «Стоп» → STT → извлечение →
серверная проверка → неизменённая расшифровка и карточки. Результат ничего не
создаёт в БД. Endpoint, STT/LLM, кеш, выбор питомца и сохранение пока не реализованы.

## Два формата

| Контракт | Назначение |
| --- | --- |
| `VoiceExtractionOutput` / `voice-extraction.schema.json` | Вывод модели: список действий, точные цитаты, исходные временные выражения, распознанное имя или ссылка на предыдущее действие; непонятые цитаты отдельно |
| `VoiceInterpretRequest` | Метаданные записи и неизменённая расшифровка для будущей интеграции |
| `VoiceInterpretResult` / `voice-command.schema.json` | Проверенный ответ клиенту: метаданные, `drafts[]`, `unparsed_fragments[]`, `result_id`, общее `requires_confirmation=true` |

В модельном формате все свойства обязательны; неизвестное значение — `null`,
пустой список — `[]`. Каждый объект закрыт через `additionalProperties:false`.
Эта отдельная схема подготовлена под Groq strict: клиентскую Pydantic-схему с
необязательными полями и defaults напрямую туда не передаём. Совместимость с
конкретной моделью/API предстоит проверить при интеграции; внешних вызовов здесь нет.

Модель не возвращает доверенные UUID, нормализованные даты, смещения подсветки,
статусы проверки или текст информационных пометок. `pet_reference_item` — индекс
с нуля в `drafts` модельного ответа, только на предшествующий элемент. Backend
проверяет смысл связи и конвертирует её в `pet_from_draft_id`.

## Черновик и проблемы

| Поле | Правило |
| --- | --- |
| `intent` | Только `create_task` / `log_care`; нераспознанное намерение уходит в `unparsed_fragments` |
| `due_at` / `occurred_at` | Срок задачи / время факта; одновременно заполнять нельзя. RFC 3339 с offset |
| `time_status` | `resolved`, `no_deadline`, `missing`, `ambiguous` |
| `pet_name` | Неизменённая распознанная форма, например «Марса»; при местоимении может быть `null` |
| `pet_id` | UUID после проверки существования и доступа сервером; одной проверки типа UUID недостаточно |
| `pet_resolution` | `explicit`, `context`, `unresolved` |
| `pet_candidates` | Доступные варианты: UUID, имя, вид, доступная дополнительная подпись `subtitle`; фото может дополнять UI позже |
| `notices[]` | Только информация: `pet_from_context`, `time_corrected`. Не блокирует подтверждение набора |
| `problems[]` | Блокирующие причины: поле, код, пояснение; требуется уточнение или поддержка функции |
| `recurrence_text` | Точная исходная цитата повтора либо `null`; явный повтор обязательно сопровождается проблемой `recurrence/unsupported` |

`missing_fields` заменено на `problems`, которые различают отсутствие,
неоднозначность, несуществующего питомца, некорректное время, неоднозначную привязку
и неподдерживаемую функцию. `recurrence` v1 заменено исходной цитатой: неподдерживаемый
повтор не превращается молча в разовую задачу.

Для задачи явное «Без срока» даёт `no_deadline`, обе даты `null`, доказательство
в `time_spans` содержит «без срока». Отсутствие времени — `missing`, неоднозначное
«вечером» — `ambiguous`; даты `null`, проблема по времени обязательна. У факта ухода
`no_deadline` недопустим. Расширение вариантов фразы «без срока» согласуем отдельно.

Однозначное «с ним» разрешаем: UUID Марса + `pet_from_draft_id` + пометка
«Марс — из предыдущей фразы». Отдельного подтверждения питомца нет; позже
подтверждается весь набор. Если связь неоднозначна или одинаковые клички не
различимы, `pet_id=null`, `pet_resolution=unresolved`, `problems` содержит причину.
Прототип показывает кандидатов и проблему; интерфейс выбора появится позже.

`has_blocking_problems` — Python property, не дополнительное поле JSON: на клиенте
блокировку определяют непустые `problems` и `unparsed_fragments`. Даже полностью
разобранный набор требует общего подтверждения перед будущим сохранением.

## Расшифровка и подсветка

`event_span`, `action_span`, `time_spans[]` используют UTF-16 и полуинтервалы
`[start,end)`, каждый содержит точную `quote`. Диапазоны относятся только к
`transcript_revision` и неизменённому `transcript` своего ответа. Подсветки питомца нет.
Для исправления времени можно передать несколько диапазонов и пометку `time_corrected`;
при неоднозначной поправке — `time_status=ambiguous`, дата `null`, блокирующая проблема.
Общий временной контекст может находиться вне диапазона отдельного события.

Backend проверяет границы, целостность surrogate pair и точное совпадение цитаты.
Неоднозначные вхождения не выбирает по первому совпадению: соответствующий диапазон
`null` (или `time_spans=[]`) и проблема `source/ambiguous_span`. У непонятого фрагмента
при неоднозначной позиции сохраняется исходная `text`, `span=null`, причина
`ambiguous_span`. JSON Schema не заменяет Pydantic-валидаторы и семантическую проверку.

## Опорная дата, ревизии и повторы обработки

- `recording_started_at` и IANA `timezone` фиксируются при начале записи.
  «Сегодня»/«завтра» считаются от локальной даты этого момента, не от окончания STT
  или текущего времени сервера. Полночь не сдвигает опору.
- `revision` — ревизия разбора; `transcript_revision` — ревизия расшифровки.
  Повторный разбор того же текста увеличивает только `revision`. Изменённый текст
  требует новой `transcript_revision` и новой `revision`; диапазоны пересчитываются.
  Ни одно из этих действий не меняет опору записи.
- Будущий кеш: память процесса, 15 минут от первого принятия ключа
  `(authenticated_user_id, recording_id, revision)`. Часы TTL монотонные,
  `recording_started_at` не используется для отсчёта TTL.
- Одинаковое содержимое возвращает тот же результат и ID. Изменение текста,
  `transcript_revision`, опоры или timezone с тем же ключом — `409`.
- Технический сбой позволяет продолжить незавершённый этап той же ревизии,
  сохранив уже завершённые этапы; параллельные запросы не запускают этап дважды.
- Намеренный новый разбор готового результата требует новой `revision`.
  После TTL — явная ошибка `410 voice_result_expired`, без повторного вызова модели.
  Реализация должна различать истёкший и новый ключ (метка истечения/жизненный цикл
  записи); простое удаление словаря через 15 минут этому правилу не соответствует.
  Потеря состояния после перезапуска тоже не должна приводить к тихому переразбору.

Это правила будущей интеграции, не реализованный кеш. Pydantic проверяет метаданные
одного сообщения; неизменность опоры между запросами обеспечит будущий обработчик.

## Ответственность и интеграция

Егор: STT, извлечение нескольких действий и точных цитат, первоначальная гипотеза
связей. Backend: список доступных питомцев из авторизованного контекста, разрешение
кличек/ссылок, нормализация относительных дат, проверка цитат, UUID и прав, сборка
пометок и проблем. Список питомцев от клиента не считается источником прав доступа.
Модель/схема не доказывают правильность смысла: сопоставление дат с текстом и
проверка принадлежности UUID потребуют сервисного кода при интеграции.

Будущий voice-роутер подключается через `app/api/v1/router.py` к общему FastAPI;
предложение маршрута — `POST /api/v1/voice/interpret`. Сейчас он отсутствует.
Позже подтверждённый набор проходит повторную проверку прав и обычную серверную
валидацию в операциях задач/ухода. Новую подсистему сохранения здесь не вводим.
